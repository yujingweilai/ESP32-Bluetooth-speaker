# ESP32 测试与压力验证 Skill

## 适用场景

当用户提出以下任一需求时，立即调用本 Skill：

- 需要对 ESP32 固件进行测试、验证、回归、联调或压力评估
- 需要检查 ESP-IDF、ESP-ADF、FreeRTOS、LVGL、Wi-Fi、蓝牙、PSRAM、外设状态
- 需要确认某次代码修改是否引入卡顿、内存异常、队列阻塞、音频中断、事件丢失
- 需要根据最近一次修改内容执行局部测试，或根据提示词执行全量测试
- 需要分析“改动会影响哪些关联功能”，并补做关联验证

如果用户没有明确测试范围，优先根据当前会话中最近修改的文件、诊断信息、报错日志、构建目标和提示词自动缩小范围；若仍无法确定，则执行全量检查。

## 核心目标

本 Skill 负责完成以下测试目标：

1. 检查 ESP-IDF、ESP-ADF、FreeRTOS 等系统环境与配置是否合理
2. 在 IDF 层检查关键外设是否初始化正确、通信是否正常、资源是否冲突
3. 在 ADF 层检查音频管道、事件监听、ringbuf、编解码、时钟链路是否正常
4. 检查堆内存、任务栈、队列、事件组、信号量、内部 RAM、外部 PSRAM 使用状态
5. 检查运行时卡顿、音频断续、任务调度抖动、显示刷新不流畅等现象
6. 检查蓝牙、Wi-Fi、FreeRTOS、LVGL 等模块是否存在冲突、竞争与回归问题
7. 执行局部或全量测试，并始终补充关联功能测试
8. 每次运行本 Skill 时，必须执行压力测试，且压力测试以“最近改动功能”为中心展开

## 执行原则

### 1. 先定位改动，再决定测试范围

- 优先读取当前会话中最近修改的文件、报错、诊断和用户提示
- 判断本次改动属于驱动层、系统层、音频链路层、显示层、连接层还是业务层
- 先做局部验证，再扩展到关联模块
- 如果改动涉及公共组件、任务调度、内存分配、事件分发、时钟、I2S、SPI、Wi-Fi、蓝牙、LVGL、PSRAM，则自动扩大回归范围

### 2. 不做“只编译不运行”的表面测试

- 只要具备执行条件，就必须进行构建验证、日志检查、运行时验证、异常路径验证
- 如果项目具备测试脚本、自动化命令、示例工程或诊断命令，优先复用现有能力
- 如果缺少现成测试入口，可以补充最小化验证代码或测试步骤，但必须遵守项目现有风格

### 3. 压力测试为强制步骤

每次调用本 Skill，都必须包含压力测试，不能省略。压力测试要求如下：

- 以“本次修改功能”为主轴
- 覆盖正常条件、边界条件、异常条件、资源紧张条件、并发条件、长时间运行条件
- 分析不同条件下会出现什么结果、带来什么影响、是否影响关联模块
- 补做关联功能测试，而不是只盯住改动点本身

### 4. 只测试，不改代码

本 Skill 的重点是测试、验证、收集证据、输出结论，不负责修改业务代码、驱动代码、组件代码或配置代码。

- 可以执行构建、体积分析、串口监视、诊断读取、日志分析、测试命令
- 可以读取工程文件、配置、脚本、日志、报错信息
- 不修改任何源码、头文件、配置文件、脚本文件
- 如果发现问题，只输出结论、影响范围、复现条件、怀疑原因、修复建议
- 除非用户后续明确要求进入修复阶段，否则停留在测试与结论层

### 5. 命令执行按需触发，默认走模拟压力测试

`idf.py build`、`idf.py size`、`idf.py monitor` 这类真实命令，不作为默认动作。

- 只有用户明确要求执行，或当前任务明确要求做真实构建/体积/串口验证时，才执行这些命令
- 如果用户没有要求真实执行，则默认不跑命令，改为进行模拟压力测试与风险推演
- 模拟压力测试需要围绕最近改动功能，分析正常、边界、异常、并发、低内存、长时间运行等场景
- 输出时必须明确标注本次属于“真实执行测试”还是“模拟压力测试”
- 不能把模拟结果表述成真实运行结果

## 标准工作流

### 第一步：识别目标平台与工程上下文

必须先确认并记录以下信息：

- 芯片型号，例如 ESP32、ESP32-S3、ESP32-C3
- 工程框架，例如纯 IDF、ADF、IDF + LVGL、IDF + BLE/Wi-Fi
- 关键版本，例如 ESP-IDF 版本、ADF 版本、组件来源
- 构建目标、分区表、sdkconfig 关键选项
- 是否启用 PSRAM、双核调度、Flash 文件系统、音频编解码、显示接口

### 证据优先级

执行判断时，优先使用以下证据来源，避免主观臆断：

1. 当前会话最近修改的文件与诊断
2. 工程中的构建脚本、README、测试脚本、sdkconfig、组件配置
3. 编译输出、运行日志、断言、回溯、性能数据
4. 用户给出的目标板、外设连接和复现步骤

如果证据不足，先说明假设，再继续做可执行范围内的验证，不要停留在空泛分析。

### 第二步：系统基础检查

围绕 ESP-IDF、ESP-ADF、FreeRTOS 进行以下检查：

- 工程是否能正常构建，依赖组件是否完整
- 关键配置是否匹配目标芯片与硬件资源
- FreeRTOS 任务优先级、栈大小、核心绑定、软硬件定时器是否合理
- Watchdog、事件循环、消息队列、事件组、信号量是否存在阻塞或饥饿风险
- 日志是否包含重复重启、断言、Guru Meditation、栈溢出、非法内存访问

### 第二步补充：按需执行 idf.py 流程

如果工程是 ESP-IDF 或 ADF 工程，且用户明确要求执行真实命令，则按以下顺序组织检查：

1. 先确认 `idf.py` 是否可用，以及当前目录是否为有效工程
2. 执行 `idf.py build`，确认编译是否通过，并记录 warning、error、组件依赖问题
3. 执行 `idf.py size`，分析 app、data、bss、IRAM、DRAM 占用是否异常
4. 如果具备串口与开发板条件，再执行 `idf.py monitor` 或等价监视流程，读取运行日志
5. 根据 monitor 输出继续判断是否存在崩溃、重启、卡顿、内存告警、驱动告警

如果用户没有明确要求执行真实命令，则改为以下默认流程：

1. 读取工程结构、sdkconfig、组件依赖、测试脚本、历史日志或报错
2. 围绕最近改动功能建立模拟压力测试矩阵
3. 推演 build、size、monitor 维度下最可能暴露的问题
4. 输出风险结论、建议观察点、建议执行命令，但不真正执行命令

执行要求：

- `build` 用于确认工程完整性和编译层问题，但默认不主动执行
- `size` 用于确认 RAM、Flash、IRAM、DRAM、PSRAM 压力，但默认不主动执行
- `monitor` 用于确认运行时问题，但只有用户需要时才执行
- 如果工程存在自定义脚本替代 `idf.py monitor`，可以复用，但要说明依据
- 输出结论时要区分“模拟推演结论”和“真实运行结论”不是同一件事

### 第三步：IDF 外设检查

根据项目实际外设进行检查，常见范围包括：

- GPIO 输入输出状态与复用关系
- UART 日志与通信链路
- I2C 设备探测、ACK、时序与上拉状态
- SPI 总线、片选、DMA、时钟配置
- I2S 主从模式、采样率、位宽、通道格式、DMA buffer
- ADC 采样稳定性、校准与噪声
- PWM、LEDC、定时器中断
- SD 卡、SPIFFS、FATFS、NVS、分区挂载
- LCD、触摸、背光、LVGL 刷新链路

检查时不仅要确认“能初始化”，还要确认：

- 是否有资源冲突
- 是否有时序风险
- 是否有 DMA/中断/缓冲区不足
- 是否在高负载下仍能稳定工作

### 第四步：ADF 音频链路检查

如果工程使用 ESP-ADF，重点检查：

- audio_pipeline 创建、注册、link 顺序是否正确
- audio_element 状态流转是否符合预期
- event listener 是否成功注册，事件是否丢失或重复
- ringbuf 大小、读写速度、背压处理是否合理
- 输入流、解码器、处理器、输出流之间的采样率和格式是否匹配
- I2S 时钟链路是否稳定，是否出现 underrun、overflow、卡顿、爆音
- pause、resume、stop、relink、restart 等流程是否存在状态机漏洞
- 多源场景下是否存在抢占冲突，例如本地播放、蓝牙输入、提示音、TTS 并发

### 第五步：内存、队列与运行时健康度检查

必须检查以下内容：

- 内部 RAM 可用量、最小剩余值、分配峰值
- 外部 PSRAM 可用量、连续大块分配能力、音频或图形缓冲是否落到正确内存区域
- heap_caps 相关内存类型分布是否合理
- 任务栈高水位，是否存在危险任务
- 队列深度、发送失败、接收超时、阻塞链路
- 事件组与信号量是否存在死锁、漏释放、优先级反转风险

如果项目涉及显示、音频、网络并发，特别关注：

- LVGL draw buffer 是否挤占内部 RAM
- 音频 DMA buffer 与解码缓存是否争抢内存
- Wi-Fi/蓝牙协议栈与应用缓冲是否造成碎片化

### 第六步：运行时卡顿与联动问题检查

必须主动检查下列现象：

- 音频播放卡顿、断续、爆音、重采样异常
- UI 刷新掉帧、触控响应变慢
- 蓝牙连接时 Wi-Fi 吞吐下降或音频抖动
- 高速日志打印导致实时任务受影响
- 文件系统读写占用导致音频链路中断
- 大块内存申请导致周期性抖动

需要明确给出：

- 触发条件
- 复现方式
- 对主功能的影响
- 对关联功能的影响
- 是否属于必修复风险

### 第七步：蓝牙、Wi-Fi、FreeRTOS、LVGL 综合检查

对以下组合场景做联合验证：

- Wi-Fi 扫描、连接、重连期间系统是否稳定
- 蓝牙扫描、配对、A2DP/HFP 或 BLE 通信期间是否影响主业务
- Wi-Fi 与蓝牙共存时是否影响音频、UI、外设响应
- FreeRTOS 多任务并发时是否出现优先级失衡、阻塞、抢占异常
- LVGL 定时刷新与外设中断、音频流、网络任务同时运行时是否卡顿

如果工程未包含某些模块，不强制捏造测试，但要明确说明未检测原因。

### 第八步：硬件可用性分级处理

如果当前环境无法直接连接开发板或外设，仍然要继续完成分级验证：

- 一级：构建检查、配置检查、依赖检查、静态路径检查
- 二级：基于日志、诊断、已有测试入口做软件侧验证
- 三级：给出最小上板验证步骤、串口观察点、预期日志和失败特征

即使暂时无法上板，也不能省略压力测试设计，至少要输出明确的压力测试方案、观察指标和预期风险。

## 专项测试模板

以下模板用于在用户指定 ADF、LVGL、Wi-Fi/蓝牙共存场景时快速展开测试。模板重点是测试步骤、观察点和结论格式，不涉及修代码。

### ADF 音频专项测试模板

适用场景：

- 用户怀疑音频播放卡顿、爆音、无声、暂停恢复异常、事件监听丢失
- 最近修改涉及 audio_pipeline、audio_element、编解码、I2S、ringbuf、蓝牙音频、TTS、提示音混播

执行顺序：

1. 默认先做音频链路模拟压力测试
2. 用户明确要求真实执行时，再执行 `idf.py build`
3. 用户明确要求真实执行时，再执行 `idf.py size`
4. 具备硬件且用户明确要求时，再执行 `idf.py monitor`
5. 根据模拟结果或真实日志补做压力测试

重点检查项：

- pipeline 创建、register、link、run、pause、resume、stop、terminate 流程
- event listener 注册是否成功，事件是否按预期到达
- 输入流、解码器、处理器、输出流的格式和采样率是否匹配
- ringbuf 容量是否过小，是否存在读写不平衡
- I2S DMA buffer 是否不足，是否出现 underrun、overflow、sample rate mismatch
- 多音源切换、提示音打断、蓝牙输入切换、本地文件播放切换时是否稳定

压力测试最少动作：

- 连续播放
- 频繁 pause/resume
- 频繁 stop/start
- 快速切歌或切流
- 音频播放同时叠加 Wi-Fi 或蓝牙活动
- 低内存条件下重复运行音频流程

必须观察：

- 是否出现卡顿、爆音、静音、尾音残留、恢复失败
- 事件是否延迟、丢失、重复
- 内存是否持续下降
- 队列与 ringbuf 是否堆积
- 对 Wi-Fi、蓝牙、UI 是否造成连锁影响

结论模板：

- 音频主链路是否稳定
- 问题主要出现在启动阶段、切换阶段还是长时间运行阶段
- 触发条件是什么
- 对主业务与关联业务的影响是什么
- 当前是否允许继续集成或烧录验证

### LVGL 卡顿专项测试模板

适用场景：

- 用户反馈界面掉帧、卡顿、输入响应慢、页面切换不顺滑
- 最近修改涉及 LVGL 页面、动画、图片资源、字体、刷屏任务、LCD/SPI/RGB 刷新链路

执行顺序：

1. 默认先做 UI 卡顿模拟压力测试
2. 用户明确要求真实执行时，再执行 `idf.py build`
3. 用户明确要求真实执行时，再执行 `idf.py size`
4. 具备硬件且用户明确要求时，再执行 `idf.py monitor`
5. 在模拟结论或真实日志基础上做 UI 高频操作与并发负载分析

重点检查项：

- LVGL tick 是否稳定
- lv_timer_handler 调度周期是否合理
- draw buffer 是否过大并挤占内部 RAM
- DMA 刷新链路是否稳定
- 页面切换、动画、列表滚动、图片解码是否引起明显峰值
- UI 线程与音频、网络、蓝牙任务是否互相抢占

压力测试最少动作：

- 高频切换页面
- 连续滑动列表
- 高频点击或触摸事件注入
- 动画、图片刷新、文本刷新同时运行
- UI 与 Wi-Fi、蓝牙、音频并发运行
- 长时间亮屏循环运行

必须观察：

- 掉帧、撕裂、触控延迟、页面白屏、花屏
- CPU 占用上升是否伴随任务饥饿
- 内存峰值是否异常
- 日志是否出现 SPI DMA、flush timeout、buffer alloc fail
- 卡顿是否只在资源加载时出现，还是常态存在

结论模板：

- 卡顿属于偶发、可复现还是持续存在
- 卡顿更偏向 CPU、内存、DMA、刷新链路还是任务调度问题
- 对用户体验的影响等级是什么
- 是否影响音频、按键、网络响应
- 当前是否建议进入功能联调阶段

### Wi-Fi/蓝牙共存专项测试模板

适用场景：

- 最近修改涉及 Wi-Fi、BLE、经典蓝牙、A2DP、HFP、Socket、MQTT、HTTP、OTA
- 用户怀疑连接不稳、吞吐下降、音频抖动、扫描时卡顿、共存互扰

执行顺序：

1. 默认先做 Wi-Fi/蓝牙共存模拟压力测试
2. 用户明确要求真实执行时，再执行 `idf.py build`
3. 用户明确要求真实执行时，再执行 `idf.py size`
4. 具备硬件且用户明确要求时，再执行 `idf.py monitor`
5. 对重连、扫描、数据传输、音频播放做并发压力分析

重点检查项：

- Wi-Fi 扫描、连接、重连过程是否稳定
- 蓝牙扫描、配对、连接、断开、重连是否稳定
- A2DP/HFP/BLE 数据通信是否被 Wi-Fi 活动干扰
- 共存状态下 CPU 占用、内存水位、队列深度是否异常
- 日志中是否出现 disconnect、timeout、coexist、buffer shortage、queue full

压力测试最少动作：

- Wi-Fi 持续传输 + 蓝牙持续连接
- Wi-Fi 扫描过程中蓝牙保持连接
- 蓝牙扫描过程中 Wi-Fi 保持业务传输
- 反复断线重连
- 网络弱信号与蓝牙业务同时运行
- 音频播放同时叠加 Wi-Fi/蓝牙并发

必须观察：

- 吞吐是否明显下降
- 连接是否频繁断开
- 音频是否卡顿或延迟
- UI、按键、外设响应是否被拖慢
- 内存与任务调度是否恶化

结论模板：

- 当前共存是否稳定
- 主要冲突出现在扫描、连接、传输还是音频阶段
- 是否存在明显互扰
- 影响哪些业务链路
- 是否建议继续叠加更多模块测试

## 强制压力测试策略

### 总原则

每次运行本 Skill，必须执行压力测试。压力测试必须围绕“当前修改功能”展开，并扩展到相关链路。

### 压力测试最少覆盖项

1. 正常负载连续运行
2. 高负载并发运行
3. 边界参数输入
4. 错误输入或异常事件注入
5. 内存紧张场景
6. 队列堆积场景
7. 长时间循环运行
8. 关联功能同时运行

### 压力测试设计方法

根据最近一次修改内容，按以下方式展开：

- 如果改动的是驱动层，重点压测初始化、反初始化、重复开关、异常参数、并发访问
- 如果改动的是音频链路，重点压测 start/stop/pause/resume、切源、重连、采样率切换、缓存极限
- 如果改动的是网络层，重点压测断网重连、弱网抖动、吞吐波动、消息风暴
- 如果改动的是 LVGL 或显示层，重点压测频繁刷新、页面切换、输入事件风暴、内存占用峰值
- 如果改动的是任务通信逻辑，重点压测队列堆积、事件风暴、超时重试、优先级冲突
- 如果改动的是 PSRAM/RAM 分配策略，重点压测连续大块申请、碎片化、峰值切换、长时间运行

### 默认压力测试矩阵

如用户未提供更细条件，默认至少补齐以下矩阵：

- 单功能独立运行
- 与关联功能双模块并发运行
- Wi-Fi + 蓝牙 + UI + 音频多模块并发运行
- 高频操作反复切换，例如重复初始化、频繁开关、快速页面切换、重复播放停止
- 低内存条件运行
- 长时间循环运行
- 错误恢复后再次运行，验证系统是否真正恢复

### 压力测试输出要求

必须回答以下问题：

- 在不同条件下分别出现什么结果
- 哪些结果是预期内的，哪些是不合理的
- 是否引发卡顿、丢包、音频中断、显示掉帧、任务超时、内存泄漏
- 对其他模块带来什么连锁影响
- 是否需要补做回归测试或结构性修复

## 局部测试与全量测试决策规则

### 局部测试

当最近修改范围明确，且影响边界可控时，至少执行：

- 改动点直接验证
- 同模块上下游验证
- 与其共享资源的模块验证
- 强制压力测试

### 全量测试

当出现以下情况时，自动升级为全量测试：

- 修改公共组件、事件分发、内存管理、底层驱动、系统配置
- 修改 FreeRTOS 调度、队列、锁、任务模型
- 修改 I2S、SPI、显示、Wi-Fi、蓝牙、PSRAM 等系统关键资源
- 当前故障无法明确定位
- 局部测试已出现跨模块异常

## 输出格式要求

执行本 Skill 后，输出内容必须至少包含：

### 1. 测试范围

- 本次依据哪些改动或提示词确定测试范围
- 为什么选择局部测试或全量测试

### 2. 执行项

- 本次测试类型，必须明确写出“真实执行测试”或“模拟压力测试”
- 实际执行的命令或检查流程，例如 `idf.py build`、`idf.py size`、`idf.py monitor`
- 未执行项及原因，例如无硬件、无串口、命令不存在、环境未初始化
- 系统检查项
- 外设检查项
- 音频检查项
- 内存与队列检查项
- 联动检查项
- 压力测试项

### 3. 结果汇总

- 通过项
- 失败项
- 风险项
- 建议修复项

### 4. 影响分析

- 当前问题影响哪些功能
- 修复后还需要关注哪些回归点

### 5. 结论

- 是否可继续集成
- 是否建议上线、合并或烧录验证
- 下一步最优先处理的问题是什么

### 使用提醒

- 测试条件要写具体，不要只写“高负载”
- 环境要写清楚芯片、框架、关键模块、最近改动点
- 测试过程要让人看得懂你是怎么一步步推演出来的
- 数据分析不能只说“可能有问题”，要说明大概会卡在哪里、先影响谁
- 每条测试总结都要有明确判断，不能只写“需关注”

## 执行细节要求

- 代码优先使用 C 语言风格，符合嵌入式工程习惯
- 日志输出使用英文
- 文档说明使用中文
- 不使用 goto
- 若需要补充测试逻辑，优先使用清晰的状态机或 switch 分支组织结构
- 必须遵守工程现有风格、构建方式和组件习惯
- 不假设某个测试命令一定存在，必须先在工程中查证
- 能运行构建、诊断、测试命令时，必须先验证再下结论
- 本 Skill 默认不修改任何代码，只做测试、分析和结论输出
- 若用户未明确要求执行命令，则默认采用模拟压力测试，不主动运行 `idf.py build`、`idf.py size`、`idf.py monitor`

## 自检要求

完成一次测试任务后，必须追加一次自检：

- 本次测试是否遗漏了关联模块
- 压力测试是否真正围绕“改动功能”展开
- 是否只验证了成功路径，遗漏了失败路径和恢复路径
- 是否检查了运行时卡顿、内存峰值、队列阻塞、并发冲突
- 输出是否清楚说明“现象、原因、影响、建议”

如果自检发现不完整，立即继续补测并更新结论，不能直接结束。

## 推荐执行语气

执行测试时，先给出场景判断，再给出检查步骤，最后给出结果与影响分析。例如：

“这是一个典型的音频链路改动回归场景。本次先验证解码链路和 I2S 输出，再补做事件监听与 ringbuf 背压检查，随后执行 Wi-Fi 并发下的压力测试，确认是否出现卡顿与内存抖动。”
