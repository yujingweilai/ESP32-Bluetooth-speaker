### Bug 1（1-2s 卡顿）的可能残留原因
方案 1 已实施，pipeline 所有元素一致暂停，恢复时应无卡顿。但有一个细节：

_reset_pipeline_ringbufs_precise() 在暂停时 reset 了所有 ringbuffer，这意味着 ringbuffer 中的预读数据被清空 。恢复时，raw → downmix 的 output_rb 是空的，downmix 设为 timeout=0（阻塞等待），但 sdcard pipeline 需要重新从 fatfs 读取 → decoder 解码 → rsp_filter 处理 → raw 输出，这个数据传播链需要时间。

对于 WAV 文件，解码几乎无延迟，但 fatfs 首次读取可能有 seek 延迟。如果文件较大且 SD 卡速度一般，1-2s 的延迟可能来自 fatfs 重新定位文件位置 。

### Bug 2（几秒后自动停止）的根因
暂停期间 mixer 反复 FINISHED/重启 是核心问题：

1. 暂停时，downmix timeout 被设为 50ms（ app_player.c:1468 ）
2. sdcard pipeline 暂停后，raw 停止产出数据
3. raw 的 output_rb 中残余数据被 downmix 消费完后，50ms 超时 → downmix 认为输入耗尽 → i2s FINISHED
4. 定时器触发 TIMER_ID_RESET_MIXER_PIPELINE ，重启 mixer
5. 重启后又设 timeout=50 ，sdcard 仍暂停 → 再次 FINISHED → 循环
6. 用户按恢复键时， play_pause() 异步执行，timeout 被设为 0
7. 但此时 mixer 可能正处于 FINISHED→重启的过渡期
8. 关键 ：重启 mixer 时 audio_pipeline_reset_ringbuffer() 会重置 downmix→equalizer 的 ringbuffer
9. 如果 sdcard pipeline 恢复后开始产出数据，但 mixer 刚好正在 reset，数据可能丢失
10. 数据丢失后，downmix 虽然设了 timeout=0（阻塞），但可能因为 pipeline 状态不一致而无法正常读取
11. 最终导致播放几秒后停止
downmix_set_input_rb_timeout(mixer, 0, index) 的含义
在 ESP-ADF 的 downmix 实现中，timeout 参数的含义是：

- timeout > 0 ：downmix 在读取输入 ringbuffer 时，如果超过指定毫秒内没有新数据，认为该输入流已耗尽，返回 0 字节读取
- timeout = 0 ：downmix 在读取输入 ringbuffer 时， 无限期阻塞等待 ，直到有数据可读
修复思路：先暂停消费者，再 abort ringbuffer 解除上游阻塞，最后暂停上游
原始代码不暂停 decoder/fatfs 的原因是：当 ringbuffer 满载时， audio_element_pause() 会让元素任务阻塞在 rb_write() 上，导致暂停操作超时或延迟数秒。正确做法是：

1. 先暂停下游消费者 （raw → rsp_filter）—— 立即生效，停止消费数据
2. abort 所有中间 ringbuffer —— 解除 decoder/fatfs 在 rb_write() 上的阻塞
3. 再暂停上游生产者 （decoder → fatfs）—— 此时它们已不再阻塞，可以立即响应 PAUSE 命令
4. reset 被 abort 的 ringbuffer —— 恢复 ringbuffer 到正常状态，为后续 resume 做准备
